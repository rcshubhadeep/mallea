# Shared live app API

Implemented by the desktop Core/host. SDK 0.4 is the canonical native app model; SDK 0.3 remains for predecessor tests and recoverable migration, not a separate Fieldnote/Parcel UI path.

## App and Surface records

Each app owns a revisioned definition with an ordered Surface collection, typed model records and an optional theme. A Surface has its own ID, title, version, lifetime, placement slot, width, visibility, optional chrome and element tree. Layout choices are columns, rows and grid; slots are header/main/footer and widths narrow/wide/auto. Stable element IDs are scoped by Surface. Repeated templates additionally receive an item index.

Core stores records in live_apps, bounded definition undo history in live_revisions, approved proposal drafts in live_drafts, pre-migration workspace snapshots in live_backups, system-owned UI definitions in live_system_surfaces, and adapter schemas/actions/primitives in live_adapter_schemas. Existing artwork/review data and grants remain in the registered domain adapters' stores, with inspectable typed model declarations in the common inventory. Model values are separate from presentation changes and are retained when a Surface disappears. Definitions and data have separate revisions; stale writes/proposals are rejected.

The same LiveApp host, Surface renderer, model/action dispatch and authoring tools run Fieldnote, Parcel and generated apps. Domain adapters implement canvas/save/review behavior only. Recovery, context menu, builder, preview and approval controls are system-owned Surface definitions; ordinary application headers/footers are app-owned Surfaces. System records cannot be edited by app proposals. Primitive internals and native window/save-dialog chrome remain implementation boundaries.

## Desktop Surface coverage

The native entry is `apps/desktop/src/main.tsx` -> `NativeApp` -> `LiveApp`. It selects app identity, not an alternate renderer. Fieldnote and Parcel migrate their ordinary headers, workspaces, inspectors and footers into app-owned Surface records. The dashboard's cards, details and catalogue are Surface trees too. Blank projects copy that same built runtime and start with no app-owned Surfaces; creation adds records rather than a separate UI implementation. Because the runtime is copied, a project created before a runtime change (such as the shared theme) keeps its old styling until `node scripts/sync-project.mjs <project-folder>` refreshes it and the project is rebuilt; its definitions and data are unaffected.

Recovery, contextual actions, Shape/approval, Sharing & Automations, model settings, project creation and concept preview use system-owned Surface definitions. These are inspectable but cannot be changed by app-owned proposals. The startup connection message also uses the Surface renderer before Core records are available.

Installed-edition policy: state includes `inferenceReady`; missing model access blocks Shape before authoring and omits model processing from the Automation processor picker, with Core checks before authoring/semantic installation. Dashboard `creationUnavailable` disables creation in its Surface presentation; Core also refuses project/app registration requests. Installed Model settings accepts a user HTTPS endpoint, exact model ID, explicit Tools/Basic JSON mode and required session key through the protected native settings path. Installed sessions start without developer environment profiles or keys. Only public model metadata/readiness enters Surface state. Quit Mallea is a system settings action and refuses shutdown while other apps are online. A bootstrap failure before rendering uses an OS-owned diagnostic dialog. See INSTALLER.md for runtime/platform limits.

Code-backed boundaries are deliberately narrow: `design-canvas` renders the registered canvas primitive; `credential-entry` is the dashboard's system-only password control; `app-preview` renders an isolated copy of the proposed Surface trees. Generic color/control internals, layout/overlay wrappers and OS chrome/folder/save pickers are renderer/native implementation. They are not independent app panels. App validation rejects unregistered components and rejects use of the credential/preview primitives inside app-owned trees. Parked browser/predecessor components are not on the native or generated-project entry path.

The regression in `tests/live-apps.test.mjs` checks all four desktop app paths, declared app/system inventories, protected system records, rejection of opaque/system component injection and removal of app presentation without model deletion. This is source/registry evidence; it does not claim arbitrary third-party native code is sandboxed.

## Supported vocabulary

- Layout: stack, row, split, grid and collapsible details.
- Content: text, image, repeated items and registered primitives.
- Controls: text input, multiline input, color, choice, checkbox, date, number and button.
- Appearance: named tokens (workspace, sidebar, card, toolbar, title, heading, muted, eyebrow, badge; primary, ghost and danger buttons) and bounded color, spacing, typography and border properties. Style values may be theme tokens (colors accent/accent-soft/ink/muted/subtle/canvas/surface/raised/line/success/warning/danger; fontSize xs-3xl; gap/padding none-xl; borderRadius none-full) or the earlier literal hex/number ranges. No arbitrary CSS/HTML/scripts.
- Theme: `theme:{accent,mode,density}` with accents olive/indigo/teal/rose/amber/slate, modes light/dark/system and densities comfortable/compact. Every app and system Surface renders through one token set in `packages/runtime/live/theme.css`; Inter and JetBrains Mono are bundled so the CSP needs no remote fonts. A record without a theme gets a deterministic default (dashboard olive, Fieldnote dark amber, Parcel indigo, blank projects an accent derived from the app ID); Core supplies it in state; authoring preserves an absent theme unless an explicit app-wide change sets it.
- Icons: Core serves each app's icon (`info.icon`) as a data URL: bundled PNGs for Core, Fieldnote, Parcel and App Store listings under `apps/definitions/icons`, generated icons under Core's private home (`icons/<app-id>.*`), and the Mallea icon as fallback. The runtime masks it to a rounded tile and passes a PNG to the native `set_app_icon` command, which sets the window/taskbar icon and, on macOS, the Dock icon (unbundled binaries otherwise show a generic one). Project creation requests one icon from the production image model when `PROD_IMAGE_MODEL` is set; failure never blocks the app. `scripts/generate-icons.mjs` regenerates bundled icons or one app's icon. Surface images accept PNG, SVG, WebP and JPEG data URLs.
- Chrome: blank-project main-slot Surfaces render as cards unless `chrome:"plain"`; built-in apps default to plain. Card chrome draws no title, so authored Surfaces start with their own title text.
- Data: text, color, boolean, number, ISO date, enum, image and bounded typed collections. New model fields may be added; changing an existing field's type requires a new field name. Values survive compatible definition changes and concurrent authoring.
- Operations: data.set, collection.append, collection.select, collection.update, collection.remove and collection.clear, plus registered adapter actions. Input bindings and button argument references are declarative; Core resolves and validates them against the current app/element. A repeat template reads item fields and can use item.index for a declared remove operation. Registered primitives expose properties/events/actions; canvas text and position events use the same typed Core event dispatcher, while pixel rendering/readiness remain native implementation details.

Generic bindings use models.MODEL.FIELD. Adapters expose their registered typed bindings through the same Surface API. Collection item templates use item.FIELD. Fields/models are owned by the app; cross-app writes are not supplied by these generic operations.

A model-backed repeat may declare `selectionBind` pointing to an app model number field initialized to `-1` (no selection). Selected rows receive a renderer outline; item templates can bind `row.selected` and `row.notSelected` for conditional content. These flags are separate from record fields. The selection binding is inspectable in element inventory.

`collection.select` takes `binding`, `index`, `selectionBinding` and optional record-field-to-editor mappings. For example, `args:{binding:"models.notes.items",index:{bind:"item.index"},selectionBinding:"models.notes.selected",text:"models.notes.draft"}` selects that record and atomically loads its text into a normal editor field. Mapping destinations are literal app-model paths, not value references. Index `-1` deselects without erasing draft text.

`collection.update` patches the selected record: `args:{binding:"models.notes.items",index:{bind:"models.notes.selected"},text:{bind:"models.notes.draft"}}`. Unmentioned record fields and other records remain intact. Core checks the app data revision, index, fields and typed values before saving. Removing an earlier record shifts declared selections; deleting the selected record or clearing/replacing the collection clears selection. Approved Automation replacement also clears selection. Selection/editor values persist as ordinary model data. Editing through selection is supported; direct `item.FIELD` inputs remain unsupported. The new select/update operations are local generic actions; they are not added to the cross-app action allowlist.

Shape's system-owned builder includes **Validation details**, showing bounded per-attempt diagnostics already returned by the authoring job. Failed proposals remain uninstalled.

Registered read-only collections may additionally declare fieldSchemas with typed item fields. Registered actions may declare parameters; button args can reference those item fields. Core resolves the current item and validates argument types before returning the registered adapter action. This powers dashboard app cards without app-specific card components. The ordinary argument/value action format remains supported. Root hiddenBind conditions also remove that Surface's layout footprint.

Dashboard-created apps have a declared `core.delete` card action and a protected `core-delete-app` confirmation Surface. The dashboard-only native capability performs deletion after exact-name confirmation and Core checks that the app is neither built-in nor running/launching/building. Deletion atomically removes Core registration, model/Surface data, drafts, undo history, grants and owned Automations. Dependent Automations in other apps are paused; their existing data is retained. Sessions, connection tickets and old credentials are invalidated, and in-flight authors cannot install late results. Project folders, generated executables and other on-disk files are retained. A one-time `dashboard-delete-v1` migration adds the control without replacing other customization.

The dashboard uses the same app/Surface registry and renderer. Its settings, project creator and concept preview are engine-owned system Surface records; only the password input and OS folder picker are primitive/native boundaries. Settings/build operations require a dashboard-only native capability, not an app-selected identity or prompt instruction. Keys never enter these records. Model selection is session-only and takes effect for subsequent jobs; running jobs finish with the configuration selected when they began. Core restart restores environment settings.

## Authoring and execution

Proposals create/extend models; add, edit, move, hide or remove Surfaces; apply targeted element changes; or change app layout and theme (`setApp` with `layout` and/or a partial `theme`; `setSurface` can set `chrome`). Theme changes are global-only: Modify this surface cannot change them. Right-click Modify this surface limits edits to that owner, with its focused element. It can add fields used by the selected Surface, but cannot rearrange or modify another Surface. Global Shape permits app-wide composition. Core enforces the scope, validates the complete resulting app, and requires approval before atomic install. App-owned Surfaces, including the canvas Surface, can be removed and re-added without deleting their data. Canvas-dependent save behavior is unavailable while its primitive is absent; framework recovery stays available.

Each install records the previous Surfaces, layout and theme (last 20 per app). **Undo last change** (`POST api/live/undo`) restores the latest entry as a new revision inside a transaction. Current models and values are kept because installs only add models, so undo never deletes data; drafts generated before the undo become stale. There is no redo.

Native hosts use authenticated app sessions. The live API exposes state, declared element events, authoring/jobs/draft/install/undo, and export under api/live. Caller identity comes from the session, not a body-selected app ID. Only the declared input/button event executes; arbitrary operation names or bindings supplied outside the registered element are rejected. Authoring receives definitions/schema context, not current private model values. A single JSON formatting fence is accepted, with the same subsequent schema/scope/behavior checks.

Inputs persist after a short idle pause; wait for Local changes saved. A button flushes pending inputs first. Preview input changes stay in a separate copy; preview buttons do not write to the service. Installation uses current saved model values, not edited preview text or an older generation snapshot.

Persistent Surfaces survive restart. Session Surfaces are removed after the last owner disconnects with a three-second reconnect grace, or when Core restarts. Their models/data remain. Context export reads the selected Surface's bindings and offers an existing saved PNG through the native destination picker. Text/JSON menu actions and their Core export endpoint require explicit startup with `node scripts/engine.mjs --dev`; normal startup omits those actions and rejects direct text/JSON export requests. The mode is process-local, defaults off on each launch and is independent of inference profile selection (`--production`). The agent cannot choose an arbitrary filesystem path. The picker reuses the [official Tauri dialog plugin](https://v2.tauri.app/plugin/dialog/).

## Resource permissions and Automation

App-specific MCP facades expose describe_app, list_surface_resources, read_surface_resource, write_surface_resource and invoke_surface_action. Resource metadata contains schema/capability declarations, not current data/default values. Discovery grants no access. Core resolves a requesting app from its authenticated session and checks the requesting Surface plus provider app/Surface/binding and separate read/write/action operation. Cross-app I/O routes through the provider's live owner socket and repeats authorization there. The engine's unrestricted legacy MCP endpoint and receiver-side legacy access switches cannot bypass this path.

Sharing marks a Surface available for requests; its owner must explicitly allow a matching grant. Grants carry a capability fingerprint so changed action arguments/schema require fresh approval. Revocation blocks later operations without erasing copied data. Removed references invalidate grants and pause dependent Automations. Tables automation_shares, automation_grants, automation_resources and automations retain the inspectable declarations/state. The current PoC uses Core's central store with logical app ownership.

An element's declared input/button capabilities determine trigger eligibility. Read-only bound elements can explicitly set observe:true to expose resource.changed; static text alone supplies no trigger. Repeated item context can resolve to its observable parent. Inputs support change/blur, presented as When I type/When I leave this field; buttons expose When I click. A choice can use optionsBind for typed collection-backed options, used by the system wizard. These capabilities do not grant cross-app access.

An Automation record contains source/event, input, processor/instruction, compatible destination, replace/append, explicit approval, enabled state and latest outcome. The trigger is owned by the installing app; its input and output can use separately approved resources. Processors are copy, emails and muse. Copy transfers compatible typed data; emails extracts locally; the shared model transforms selected text into validated text or a text-field collection. Registered artwork/review adapters expose typed bundles without UI-tree exchange. Action invocation is limited to declared local data.set, collection.append and collection.clear buttons and returns an execution acknowledgement, not the owner's model.

Typing waits 700 ms after a persisted event; each Automation has one in-flight run and coalesces newer input. Muse makes one request with the selected shared configuration, 1,200 output tokens maximum, a 60-second timeout, input text truncated to 2,000 characters, instruction up to 500 characters and at most 20 collection items. No automatic retry/fallback. Current schema, grants, owner presence, source stamp and destination stamp are checked before commit. Pause, stale output and failed requests cannot replace newer data. Origin tracking/unchanged-value checks prevent copy echo loops; append skips repeated identical applied input. Outcomes and enabled definitions persist. Muse does not run merely because Core restarts; approved copy subscriptions can reconcile on reconnect.

The builder/manager are system-owned Surface definitions using the ordinary renderer. Sharing, requesting, owner approval and activation are separate actions. See REHEARSAL_E004.md for exact tests and the one-time runtime upgrade for older generated projects.

## Boundaries

A001 adds `ask_user` to the live tool author. Core validates bounded questions and exposes a fixed system-owned session Surface on the owning app's job; it is never a model-authored arbitrary panel or a persistent app definition. `POST api/live/jobs/{id}/answers` accepts the exact pending batch ID and one valid answer per question. GET inspects jobs; POST answers/cancels. Core rejects wrong-app, replayed, stale, cancelled and expired submissions. No answer implies installation or permission approval. Waiting retains the pinned draft, scope/focus, model configuration and cumulative budgets; only the active-time clock pauses. Pending questions expire after 30 minutes, recover on renderer reload within the live session and cancel after the last owner exceeds reconnect grace. Core restart discards them; unsubmitted answers stay local to the temporary panel. Existing Basic JSON remains explicit and does not gain the ask-user tool. Checks, exact limits and user steps: [REHEARSAL_A001.md](REHEARSAL_A001.md).

C001 authoring uses explicit Core-owned policy: `intent:add` (default) preserves all existing Surfaces/models/theme/layout and appends new Surfaces with `placement:independent`; `intent:app` permits app-wide operations. A selected `surfaceId` always narrows to that Surface, regardless of intent. Scoped jobs can create models but cannot extend existing ones. Independent additions cannot reference existing models or invoke adapter primitives/actions; app-wide mode is the explicit way to request coupling. The renderer places independent contributions after the existing header/main/footer groups and reserves scrollbar space. Existing sibling keys, definitions and bindings remain stable. App-wide `setSurface` may explicitly change placement back to `flow`.

Live authoring defaults to the tool loop in `services/workspace/live-author.mjs`. Initial context is a compact app/Surface/model inventory and trusted scope/focus. `lookup_api` returns validator-derived operation/node/element-edit schemas or the API overview and registered contract. `inspect_surface` and `inspect_model` provide definitions with initial values instead of live values. `apply_draft`, `validate_draft`, `finish_draft` and `unsupported` operate on a pinned private snapshot; finish saves a preview, never installs. Core replays stored authorized operations and compares the artifact again inside the install transaction, retaining current model values. Legacy unscoped drafts retain earlier semantics. Limits, evidence and exact user checks: [REHEARSAL_C001.md](REHEARSAL_C001.md).

Dashboard-only settings now accept a user-configured HTTPS Chat Completions URL, exact arbitrary model ID and session key. The same selection supplies authoring and semantic Automation; the stored `muse` processor ID is retained for compatibility. Tools mode requires function calls; explicitly selected Basic JSON preserves the three-attempt flow and full sanitized definition context. There is no automatic fallback between modes/models. Custom profiles and keys are memory-only; environment profiles return on restart. Keys never enter authoring context or Surface/model records. Provider-specific features and real model quality are not established by mocked protocol checks.

Vocabulary and registered operations are intentionally small. No arbitrary native code, expressions, schema type replacement, general workflow scheduler or remote sharing. Automation supports one transformer, not a general graph editor. Core/apps trust the same OS user; the owner protocol is not hostile-process isolation. Windows native checks are recorded separately from unit tests and user acceptance. macOS native builds and local launch have been checked; user acceptance of the new collection-editing flow remains pending. Linux native execution is untested.
